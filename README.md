# INTC Supporter

Локальный каркас студенческого портала: React + TypeScript + Vite, Python + FastAPI, PostgreSQL 17, Docker Compose.

## Быстрый запуск

Каждый сервис имеет собственный Dockerfile:

- `client/Dockerfile` — React + TypeScript + Tailwind CSS на Node.js.
- `api/Dockerfile` — FastAPI на Python с запуском миграций Alembic.
- `db/Dockerfile` — PostgreSQL на основе официального образа `postgres:17-alpine`.

Корневой `compose.yaml` собирает и запускает все три сервиса, задаёт подключения и сохраняет данные БД в томе.

Из корня проекта в PowerShell:

```powershell
Copy-Item .env.example .env
docker compose up --build -d
docker compose ps
```

Открыть сайт: http://localhost:5173. Swagger API: http://localhost:8000/docs. Проверка БД: http://localhost:8000/api/v1/health. Порты меняются в `.env`.

Это среда разработки с hot reload, локальными паролями и портами, привязанными к localhost. Данные PostgreSQL сохраняются в именованном томе. Миграции автоматически выполняются перед запуском API. Остановка с сохранением данных: `docker compose down`. Не добавляйте `-v`, если данные нужно сохранить.

В Docker у фронтенда включён `VITE_USE_POLLING=true`: Vite проверяет изменения файлов каждые 500 мс, чтобы обновления из Windows надёжно попадали в браузер. При запуске вне Docker polling по умолчанию выключен.

PostgreSQL доступен локально на порту 55432 (внутри Docker — 5432); том PostgreSQL 17 подключён к `/var/lib/postgresql/data` согласно [документации официального образа](https://hub.docker.com/_/postgres).

## Что уже есть

- Адаптивный интерфейс: главная, расписание с группой и датой, документы, приложения, информационный экран ИИ-чата.
- Чтение контента из PostgreSQL: `GET /api/v1/documents`, `GET /api/v1/applications`, `GET /api/v1/schedule?group=ИС-23-1&day=2026-11-17`.
- Ручное заполнение расписания на `/schedule`: группа и дата → «Заполнить / изменить расписание дня» → таблица пар → публикация. Можно добавлять, исправлять и удалять строки; группа и дата заблокированы на время редактирования. У студента группа подставляется из аккаунта.
- `PUT /api/v1/schedule?group=...&day=YYYY-MM-DD` заменяет расписание выбранного дня одним сохранением; пустой `lessons` очищает этот день. Сервер проверяет права на группу, статус аккаунта, Origin, обязательные поля, время и пересечения. Остальные группы и даты не меняются.
- Загрузка фото расписания (см. раздел ниже): ИИ распознаёт таблицу на русском и казахском, пользователь проверяет результат и публикует его для группы.

Публиковать расписание может администратор — для любой группы, и студент — только для своей группы; опубликованное видит вся группа. У каждой пары сохраняется автор (`lessons.created_by_id`). Название группы нормализуется: «тис 24p», «ТИС - 24Р» и «ТИС-24Р» — одна группа (регистр, пробелы, латинские буквы-двойники).
- `GET /api/v1/health` проверяет реальное соединение с БД.
- SQLAlchemy-модели и Alembic-миграции: `users`, сессии, документы, пары, приложения.
- Вход и регистрация на `/auth`; кнопки в шапке и ссылки в закрытых разделах.
- `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`.
- `POST /api/v1/chat` отдаёт потоковый текстовый ответ по документам колледжа. Без `AI_API_KEY` возвращает 503; без доступных текстов документов сообщает об отсутствии информации.

Студент: фамилия, имя, почта, пароль, группа, роль `student`. Администратор: фамилия, имя, почта, пароль, роль `admin`, без группы. Оба типа хранятся в `users`; миграция `0002` переименовывает прежнюю таблицу `students` с сохранением данных. Публичная регистрация создаёт только студентов. Пароль (8–128 символов) хранится как scrypt-хеш; почта нормализуется и уникальна.

После регистрации пользователь переходит к форме входа. Доступ открывается после входа; предварительное одобрение не включено. Сервер проверяет статус на каждом запросе к контенту: заблокированному аккаунту возвращается 403. Состояние `pending` сохранено для совместимости и также закрывает доступ. Админ-интерфейс блокировки пока не реализован.

Сессия хранится в HttpOnly / SameSite=Strict cookie, в БД — только SHA-256-хеш случайного токена. Выход отзывает сессию; срок по умолчанию 7 дней. Для HTTPS задайте `COOKIE_SECURE=true`; срок регулируется `SESSION_LIFETIME_SECONDS`. POST-запросы авторизации проверяют Origin. Данные входа не хранятся в localStorage.

Создание администратора вручную (пароль вводится скрыто, не хранится в репозитории):

```powershell
docker compose exec api python -m app.create_admin --email admin@example.com --first-name Алексей --last-name Панченко
```

Команда отказывается менять существующий аккаунт. При первоначальном запуске база пустая; тестовый администратор текущего окружения создан отдельно. Загрузка файлов и управление остальным контентом остаются следующими этапами.

Расписание можно заполнять вручную на конкретную дату или импортировать из изображения. Импорт Excel отложен.

Каталог приложений — сетка из восьми начальных карточек с логотипами, стоимостью и описаниями RU/KZ. Карточка ведёт на официальную страницу скачивания. Администратор управляет каталогом прямо на странице; миграция `0009` добавляет поля и начальные записи и поддерживает обе прежние истории миграции `0003`. Интерфейс всех текущих страниц переведён на русский и казахский, кнопка RU/KZ сохраняет выбор между посещениями. Исходные документы и данные расписания автоматически не переводятся. См. [каталог, API и языки](docs/application-catalog.md).

Основная ветка репозитория — `master`. Изменения из рабочих веток объединяются в неё; новые pull request следует направлять в `master`.

## Расписание по фото

На `/schedule` кнопка «Загрузить фото расписания» → выбор PNG/JPEG/WebP (большие фото сжимаются в браузере до 2400 px, мелкие скриншоты увеличиваются до 1600 px — иначе модель путает казахские буквы и похожие фамилии) → таблица с распознанными строками → правка → «Опубликовать».

1. `POST /api/v1/schedule/recognize` `{"image": "data:image/png;base64,..."}` — отправляет фото в модель с JSON-схемой (structured outputs) и возвращает черновик. В базу ничего не пишет. Ограничение — 20 распознаваний в час на пользователя, фото до 8 МБ.
2. `POST /api/v1/schedule/import` — публикует проверенный черновик. Сервер заново валидирует всё: время, пересечения после раскладки по неделям, права на группу.

Два вида документов:

- `weekly` — недельная сетка («6 учебных недель»). Строка: `weekday` (1 = Пн), `pair`, `starts_at`, `ends_at`, `subject`, `teacher`, `room`, `week`, `note`. Публикация: `{"kind": "weekly", "group", "start_date", "weeks", "lessons"}` — расписание группы за весь период заменяется.
- `dated` — расписание по датам (практика). Строка: `date` вместо `weekday`. Публикация: `{"kind": "dated", "group", "lessons"}` — заменяются только эти даты, в остальные дни остаётся обычное расписание.

Срок и начало: число недель берётся с фото («6 учебных недель» → `weeks_count: 6`), дату начала («с 10 октября») пользователь вводит сам; если она напечатана на фото, модель подставит её в `start_date`. Недели календарные (Пн–Вс): 1-я — неделя, в которой лежит `start_date`; если это суббота или воскресенье, 1-я неделя начинается со следующего понедельника (10.10.2026 → 12.10–18.10, 6 недель — по 22.11). В форме показан список недель с датами и цветом.

Чередование («мигание»): `week: "odd"` — **чёрный** вариант, недели 1, 3, 5…; `"even"` — **красный** вариант, недели 2, 4, 6…; `"every"` — каждую неделю. Разделённая вертикальной линией ячейка: левая половина — `odd`, правая — `even`. Красная дата/ФИО внутри ячейки даёт две строки (чёрный и красный преподаватель), красная дата сохраняется в `note`.

Модель задаётся `AI_VISION_MODEL` (по умолчанию `gpt-6-luna` — экономичная модель с поддержкой изображений и Structured Outputs), использует те же `AI_API_KEY` и `AI_BASE_URL`, что и чат. `AI_VISION_REASONING_EFFORT` оставлен `low`. Ответы модели могут немного отличаться от запуска к запуску, поэтому шаг проверки перед публикацией обязателен. Логика раскладки по датам не зависит от модели: она в `api/app/schedule_import.py`, контракты — в `api/app/schedule_schemas.py`, промпт — в `api/app/schedule_ai.py`.

ИИ-чат и распознавание используют OpenAI-совместимый API. Для Docker задайте `AI_API_KEY` в корневом `.env`; для запуска Python вне Docker — в `api/.env`. Официальный OpenAI API использует `AI_BASE_URL=https://api.openai.com/v1`; модель чата задаётся через `AI_MODEL`, распознавания — через `AI_VISION_MODEL`. Ключ не добавлять в Git и не отправлять в сообщения. После изменения настроек Docker выполните `docker compose up -d --force-recreate api`. Чат читает PDF по записям `documents`, а при пустой таблице использует `api/knowledge/*.pdf`. Это начальная реализация с ограничением объёма контекста, без векторного поиска и ссылок на источники в ответе. Для сканов без текстового слоя OCR пока отсутствует.

## Структура

Фронтенд организован по FSD, вёрстка на Tailwind CSS. Описание слоёв и команд форматирования: [архитектура фронтенда](docs/frontend-architecture.md).

```text
client/src/             интерфейс
api/app/                настройки, модели, схемы, API
api/migrations/         версии схемы БД
api/tests/              проверки API
docs/design-prompt.md   промпт для дизайна
docs/project-questions.md вопросы по требованиям
compose.yaml            локальная инфраструктура
```

## Работа без контейнеров приложений

PostgreSQL остаётся в Docker. Для Python рекомендуется 3.13+, Node.js 24.

```powershell
docker compose up -d db
python -m venv .venv
.\.venv\Scripts\python -m pip install -r api/requirements-dev.txt
Copy-Item api/.env.example api/.env
cd api
..\.venv\Scripts\python -m alembic upgrade head
..\.venv\Scripts\python -m uvicorn app.main:app --reload
```

В другом терминале из `client`: `npm ci`, затем `npm run dev`. Vite проксирует `/api` на `http://127.0.0.1:8000`, поэтому отдельная настройка CORS для этого сценария не нужна. При изменении порта БД обновите `api/.env`.

## Команда из пяти человек

Предлагаемое распределение: 1) интерфейс и дизайн-система; 2) расписание и каталог; 3) регистрация, вход, права и админ-проверка; 4) документы и RAG; 5) Docker, миграции, интеграция и проверки. Согласуйте API-контракты через Swagger, берите отдельную ветку под задачу, изменения схемы БД оформляйте миграциями.

Для новой миграции из `api`: `python -m alembic revision --autogenerate -m "description"`; проверьте файл перед `python -m alembic upgrade head`. Для API-тестов из `api`: `python -m pytest`. Сборка фронтенда из `client`: `npm run build`.

Следующие этапы: управление аккаунтами и контентом, развитие поиска по документам и добавление ссылок на источники в AI-ответах.
